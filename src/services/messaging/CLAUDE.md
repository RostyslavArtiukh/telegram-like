# Messaging service (port 8084, DB `telegramlike_messaging`)

Messages, reactions, read receipts. 4 projects, namespace `TelegramLike.Messaging.*`.

## Domain
- **Indexes** (declared via `IMongoIndexes`, see the root guide): `messages` → `(ChatId, SentAt desc)` (`chat_messages_by_recency`, [TL-121]) — `GetChatMessages` is the hottest read here and without it every page is a collection scan plus an in-memory sort, which Mongo aborts past 32 MB; `message_read_receipts` → unique `(MessageId, MemberId)`; `hidden_messages` → `(UserId, MessageId)` ([TL-122]) — the per-page hide lookup asks only about the ids on that page, instead of pulling everything the reader ever hid in any chat; `chat_memberships` → `(ChatId, IsActive, UserId)` ([TL-123]) for `GetActiveMemberIds`, which runs on **every send**. `chat_types` declares none on purpose — its `_id` is the chat id and every access is a point lookup. `MessageIndexTests` explains the real paging query and fails on a `COLLSCAN`/`SORT` plan, because a missing index still returns correct results on a small database.
- `Message` aggregate = one document; `Reaction` embedded. Reaction/retract writes go through the aggregate and use **optimistic concurrency** ([TL-74b]): a `Version` field guards the `ReplaceOne` and callers retry via `ConcurrencyRetry` — so concurrent reactions don't lost-update. `HideMessage` → `hidden_messages` read-model. Read receipts: unique `(MessageId, MemberId)` index makes them idempotent; Broadcast additionally does an atomic `$inc broadcastReadCount` on the message, once per new receipt.
- Publishes through the shared outgoing-events queue (`TelegramLike.Shared.Infrastructure`, collection `outgoing_events`) via one switch, `MessagingIntegrationEvents.Map`, handed to `AddOutgoingEvents`; an event with no arm there never reaches the wire (pinned by `MessagingIntegrationEventsTests`). Publishes `MessageSent` (carries **embedded recipients**), `MessageRetracted`, `ReactionAdded/Removed` (`Emoji` crosses as its name — `Contracts` cannot see the domain enum). Query `GetChatMessages` = keyset paging by `SentAt` DESC.

## Server-side enrichment (was BFF-supplied)
Cross-context values are derived server-side from local read-models / the signed JWT, not trusted from the client:
- **SendMessage is now hybrid fail-closed** ([TL-70]): a local `chat_memberships` read-model (event-sourced from `MemberJoined/Kicked/Left`, Presence-style) drives it. If the chat is materialized and the author isn't a member → `UnauthorizedAccessException` (403). **Recipients come only from the read-model** ([TL-118]) — the `recipients` field left the wire entirely, so no caller can supply or spoof an audience and no UI host keeps a second copy of the derivation. An unmaterialized chat (legacy / MemberJoined in flight) still fails **open** on membership so a just-created chat's first send isn't rejected, but it has no known audience: that message is stored and readable while raising no notification or realtime push. Accepted, logged as a warning, and pinned by `Send_UnknownChat_StoresTheMessageButFansOutToNobody`.
- **Retract moderator authority is server-side** ([TL-74b]): the read-model materializes member `Role` (from `MemberJoined` + `MemberRoleChanged`), and `RetractMessage` derives Owner/Admin via `IsModeratorAsync` — the caller's `retractedByModerator` flag is ignored (kept on the wire for compat). Reads (`GetChatMessages` / `GetMessageById`) enforce membership fail-closed for materialized chats.
- **Ban and chat deletion revoke access here too**: `MemberBannedConsumer` deactivates the member and `ChatDeletedConsumer` deactivates the chat's whole membership (`DeactivateChatAsync`, one `UpdateMany`, no upsert). Without these the read-model would still call a banned user an active member and keep accepting messages, reactions and retracts in a deleted chat — Chats' own `DeletedAt` only guards Chats.
- **Membership now fail-closed** ([TL-101]): `AddReaction` / `RemoveReaction` / `MarkAsRead` and `RetractMessage`'s membership check reject non-members with `ForbiddenException` (403) — safe now that the `chat_memberships` read-model is backfilled for pre-existing chats via the admin-triggered `ChatMembershipsSnapshotIntegrationEvent`.
- **Server-side enrichment complete** ([TL-102]): `MarkAsRead` derives `isBroadcast` from the loaded message (`BroadcastReadCount != null` → `Message.IsBroadcast`); `SendMessage` derives it from a `chat_types` read-model (event-sourced from `ChatCreatedIntegrationEvent` + backfill), caller flag used only for a not-yet-materialized chat then ignored; `AddReaction`'s premium is read from the signed `premium` JWT claim (`ApiControllerBase.CurrentUserIsPremium`), not the body. The request DTOs no longer carry these fields; SDK/BFF/MAUI stopped sending them.

## Endpoints
`POST /messages/`, `GET /messages/{id}`, reactions add/remove, `{id}/retract`, `{id}/read`, `{id}/hide`, `GET /chats/{id}/messages`.

Controllers (`Controllers/`): `MessagesController` (lifecycle + queries) + `MessageReactionsController` + `MessageReadReceiptsController`, on `ApiControllerBase`; `DomainExceptionFilter` (`ValidationException`/`DomainException`→400, `ForbiddenException`→403, `ProblemDetails` + `traceId`); handlers/domain throw those semantic types (in `Messaging.Domain`), **not** raw BCL exceptions — a framework `InvalidOperationException`/`ArgumentException` now → 500. `JsonStringEnumConverter` kept — **load-bearing** for `Emoji`/`AttachmentType` on the wire (the BFF sends/reads names). BFF-enriched params live in the `Contracts/` request records. See the `api_controllers` memory.
